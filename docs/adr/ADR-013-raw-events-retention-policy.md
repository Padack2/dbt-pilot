## 1) 배경 (Context)

- `raw_events`는 5분 주기 배치가 계속 INSERT만 하고 삭제 로직이 없어 무기한 쌓인다. Neon
  무료 티어 용량 한도에 곧 도달할 것으로 예상되어 대응이 필요했다.
- 결제(유료 플랜/다른 유료 호스팅)는 토이/포트폴리오 프로젝트 성격상 부담스러워 배제.
- 목표: 결제 없이 저장 용량 증가를 막는다.
- 비목표: raw_events의 장기 보관·재처리(과거 전체 기간 `--full-refresh`) 지원. 이 프로젝트는
  정확한 분석보다 파이프라인 구현 자체가 목적이라(README "배경 및 한계" 참고) 원본 데이터의
  영구 보관 우선순위는 낮다고 판단.

## 2) 고려한 선택지 (Options)

- 옵션 A: 다른 무료 Postgres 호스팅으로 마이그레이션
    - 장점: 코드 변경 없음
    - 단점/리스크: 어느 무료 티어든 저장 용량 한도가 비슷해서(대략 0.5GB대) 같은 문제가
      다시 재발할 뿐, 근본 원인(무한정 append)은 그대로 남음. 마이그레이션 작업 자체도
      1회성 비용이 듦
- 옵션 B: `raw_events`에 보존 기간을 두고 오래된 행을 주기적으로 삭제 (채택)
    - 장점: 근본 원인 해결, 코드 몇 줄로 구현 가능, 기존 5분 주기 파이프라인에 자연스럽게
      얹을 수 있음
    - 단점/리스크: 보존 기간이 지난 원본 이벤트는 영구히 사라짐. `dbt build --full-refresh`로
      `precomputed_events`를 처음부터 다시 만들면 삭제된 구간만큼 데이터가 비게 됨
- 옵션 C: 오래된 행을 삭제 대신 별도 아카이브 테이블/스토리지로 이관
    - 장점: 원본 보존과 용량 절감을 동시에 달성
    - 단점/리스크: 결국 그 아카이브도 어딘가의 저장 용량을 차지하므로 문제를 옮기는 것에
      가까움. 이 프로젝트 규모에서 별도 아카이브 파이프라인을 유지보수할 실익이 작다고 판단

## 3) 결정 (Decision)

- 최종 선택: 옵션 B. `raw_events`에서 `created_at`이 **7일**보다 오래된 행을 삭제하는
  dbt 매크로 `prune_raw_events(days=7)`를 추가하고, 매 파이프라인 실행(5분 주기)마다 MV
  refresh 다음 단계로 실행한다.
- 결정 이유(Trade-off): `precomputed_events`의 incremental 워터마크는 `raw_events`가
  아니라 자기 자신(`precomputed_events`)의 `max(created_at)` 기준이므로, `raw_events`를
  지워도 평상시 5분 주기 incremental 실행에는 전혀 영향이 없다. 잃는 것은 오직
  `--full-refresh` 시 재구성 가능한 히스토리 범위뿐이고, 이 프로젝트에서 그 시나리오의
  가치보다 결제 없이 용량 문제를 없애는 실익이 훨씬 크다고 판단했다. 보존 기간을 30일이
  아닌 7일로 짧게 잡은 것도 같은 이유 — 정확한 장기 분석이 목적이 아니라서 굳이 여유
  있게 가져갈 필요가 없었다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: `raw_events`가 최대 7일치로 상한선이 생겨 저장 용량이 더 이상 무한정
  늘어나지 않음. 매 실행마다 그날그날의 경계 구간만 지우므로 삭제 배치 크기가 작고 가벼움
- 부정적 영향/부채: `/explorer`에서 raw_events를 조회할 때 7일보다 오래된 이벤트는 더 이상
  보이지 않음(단, 날짜 필터 UI가 없어 사용자가 "없어졌다"고 헷갈릴 지점은 적음).
  `dbt build --full-refresh`를 돌리면 7일 이전 구간의 `precomputed_events`/MV 데이터가
  전부 비게 됨 — 현재는 이 프로젝트에서 full-refresh를 실행할 계획이 없어 감내 가능
- 추후 작업(TODO): 만약 나중에 저장 공간이 더 여유로워지거나(유료 전환) 장기 트렌드
  분석이 중요해지면 보존 기간을 늘리거나 옵션 C(아카이브)로 전환 검토

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 파이프라인 실행 로그에서 `Pruned N raw_events rows older than 7 days` 확인.
  `select min(created_at), max(created_at) from raw_events;`로 최솟값이 항상 현재 시각
  기준 7일 이내인지 주기적으로 확인
- 롤백 전략: `.github/workflows/ingest.yml`의 "Prune raw_events" 스텝만 제거하면 즉시
  삭제가 멈춘다(매크로 파일은 남겨둬도 무해함). 이미 삭제된 데이터는 복구 불가
